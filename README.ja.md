# goals-iterm-mcp

[プロジェクトサイト](https://lucky-goals.github.io/goals-iterm-mcp/)
[English](README.md) | [简体中文](README.zh-CN.md) | [繁體中文](README.zh-TW.md) | 日本語

**コーディングエージェントで Mac 上の CLI を操作。スマートフォンからでも開発を進められます。**

goals-iterm-mcp は **iTerm2 の Python API** を通じて、MCP 対応エージェントを Mac 上のターミナルに接続します。会話でタスクを伝えると、エージェントがターミナルウィンドウを開き、プロジェクト内で別のコーディング CLI を起動し、指示を送り、進捗や結果を読み取れます。複数のプロジェクトや CLI セッションで進める vibe coding の作業を、ターミナルを手動で切り替えずに調整できます。

## できること

- **スマートフォンから作業を続ける**：エージェントのモバイル版やリモート接続を通じて、Mac 上の iTerm2 に作業を指示できます。接続先のエージェントがローカル MCP にアクセスできることが条件です。
- **コーディング CLI を連携させる**：Claude Code、Codex CLI などを起動し、プロジェクトを選んで開発や調査のタスクを送れます。
- **会話で進捗を確認する**：ウィンドウやタブの一覧、ターミナル出力を読み取り、各セッションの状況を要約できます。
- **プロジェクトごとにセッションを分ける**：専用のウィンドウやタブを作成し、明示的な ID で操作対象を指定できます。
- **目標の達成までほかの CLI を継続的に指導する**：Codex や Claude などの監督役のエージェントに、目標と明確な完了条件を与えます。エージェントはこの MCP でほかの CLI セッションを確認し、進捗を判断し、追加の指示を送り、結果を検証するサイクルを繰り返せます。目標の管理と継続実行は監督役のエージェントが担い、この MCP はターミナルへのアクセスを提供します。

想定する流れは、**スマートフォンまたはデスクトップでの会話 → ローカル MCP にアクセスできるエージェント → iTerm2 → コーディング CLI** です。Codex、Claude、Cursor、WorkBuddy、Trae、Hermes など、利用するクライアントがローカル stdio MCP と必要なモバイル・リモート接続に対応していれば、この構成を使えます。手動検証では Codex デスクトップから iTerm2 内の Claude Code と Codex CLI を操作しました。

たとえば、監督役のエージェントに次の目標を伝えます。

> プロジェクト専用の iTerm セッションで動くコーディング CLI を、ログイン問題の原因調査、修正、関連テストの合格まで継続的に指導してください。各段階で進捗を確認し、必要に応じて追加の指示を送り、最後に完了条件と結果を照合してください。実行中のタスクを重複して送らないでください。この範囲を超える判断が必要な場合は私に確認し、完了時に変更内容とテスト結果を報告してください。

公開済みの 0.2.0 パッケージは 12 個の stdio MCP ツールを提供します。従来のセッション一覧、ターミナルの読み書き、ウィンドウとタブの作成、セッションの命名に加えて、4 個の終了ツールがあります。`main` ブランチのソースには、未公開の読み取り専用増分である `inspect_sessions` も含まれるため、現在のソースは 13 ツールです。これは PyPI 0.2.0 には含まれません。ソースの契約と main 専用の監査情報は[終了ツール実装仕様](docs/closing-tools-spec.md)を参照してください。

## 事前準備

### iTerm2 Python API を有効にする

macOS 上で iTerm2 をインストールし、起動しておく必要があります。このプロジェクトは **iTerm2 3.7.6** で検証済みです。

1. **iTerm2 → Settings → General → Magic** を開きます。
2. **Python API** を有効にします。
3. MCP サーバーの初回接続時に iTerm2 の API 認可ダイアログが表示された場合は、接続を許可します。
4. MCP ツールの使用中は iTerm2 を起動したままにします。

詳しくは [iTerm2 公式設定ドキュメント](https://iterm2.com/documentation-preferences-general.html)を参照してください。

### コーディング CLI を設定する

iTerm2 経由でコーディング CLI を操作する前に、その CLI をインストールし、iTerm 環境で認証を設定してください。OAuth ログインを完了するか、CLI が対応する方法で API Gateway のエンドポイントと認証情報を設定します。まず iTerm2 で手動起動し、簡単なプロンプトに応答できることを確認してください。

新しい iTerm ウィンドウやタブにも必要な設定が引き継がれるようにしてください。goals-iterm-mcp はターミナルを操作し、各 CLI は自身の認証と API 設定を使用します。認証情報は CLI が対応する認証情報ストアやローカル設定に保存し、エージェントへのプロンプトには含めないでください。

## uvx で実行する

バージョン 0.2.0 は [PyPI](https://pypi.org/project/goals-iterm-mcp/) で公開されています。このリリースは全 12 ツールを提供します。リポジトリをクローンせずに実行できます。

```sh
uvx --python 3.12 goals-iterm-mcp@0.2.0 serve
```

Python のインポートパスは `goals_iterm_mcp`、コマンド名は `goals-iterm-mcp` です。

## エージェントとの会話でインストールする

以下のプロンプトを、ローカルコマンドの実行と MCP クライアントの設定ができるエージェントに渡してください。`[MCP クライアント]` は Codex デスクトップや Claude Code など、実際に使うクライアント名に置き換えます。ローカルの macOS へのアクセスが必要です。クラウドのみで動作するチャットからは、ローカルの iTerm2 に接続できません。

```text
PyPI から goals-iterm-mcp 0.2.0 をインストールし、[MCP クライアント] に設定してください。
リポジトリ：https://github.com/lucky-goals/goals-iterm-mcp

1. このコンピューターが macOS で、iTerm2 がインストール済みかつ起動中であることを
   確認してください。uv/uvx がなければ、uv の公式手順でインストールしてください。
   Python 3.12 を使い、リポジトリのクローンやプロジェクトの .venv は不要としてください。
2. 次のコマンドでパッケージを実行できることを確認してください。
   uvx --python 3.12 goals-iterm-mcp@0.2.0 --help
3. クライアントの既存の MCP 設定を確認し、無関係な設定を保持してください。
   ユーザーレベルの設定で、iterm という名前の stdio サーバーを追加または更新し、
   重複を避けてください。
   command：このコンピューター上の uvx の絶対パス
   args：["--python", "3.12", "goals-iterm-mcp@0.2.0", "serve"]
   クライアントが対応する設定形式と場所を使ってください。編集前に既存の設定を
   バックアップし、ほかのサーバーは変更しないでください。
4. 必要に応じて iTerm2 Python API の有効化と認可ダイアログの承認を案内してください。
   クライアントが対応する方法で MCP 接続を再読み込みしてください。
   私が手動でクライアントを再起動する必要があれば、明確に伝えてください。
5. MCP ハンドシェイク、インストール済みバージョンのツールの検出、読み取り専用の list_sessions 呼び出しを
   確認してください。インストール確認では、ターミナル入力の送信、セッション内容の
   読み取り、ウィンドウの作成や終了は行わないでください。
6. 設定ファイルの場所、起動コマンド、検証結果を報告してください。
   単体での接続成功と、対象クライアントへのツールの実際の読み込みを区別してください。
   作業が進められない場合は、残っている具体的な手順を説明してください。
```

この公開パッケージのインストールに PyPI アカウントや API トークンは不要です。上記の設定ではインストール済みバージョンのすべてのツールが提供されますが、インストール確認ではセッション一覧の取得のみを行います。

## インストール済みの旧バージョンを更新する

まず既存の `iterm` MCP 設定を確認し、バックアップしてください。同じ項目を更新し、環境変数、`--read-only`、`--session-id` の制限、ほかのサーバー設定を保持します。重複登録せず、元のインストール方式に合わせて更新してください。

### uvx を使用している場合

[PyPI のバージョン履歴](https://pypi.org/project/goals-iterm-mcp/#history)と [GitHub Releases](https://github.com/lucky-goals/goals-iterm-mcp/releases)を確認し、最新公開パッケージが起動できることを検証します。

```sh
uvx --python 3.12 goals-iterm-mcp@latest --help
```

このコマンドは **MCP クライアントの保存済み設定を変更しません**。既存の `args` にある `goals-iterm-mcp@0.1.2` などの旧指定を `goals-iterm-mcp@<VERSION>` に変更し、`<VERSION>` を確認済みの公開バージョン番号に置き換えてください。`uvx` の絶対パスとほかの引数は保持します。意図した更新と旧バージョンへの復帰を可能にするため、バージョンの固定を推奨します。

今後の起動時に最新公開版へ追従させたい場合は `goals-iterm-mcp@latest` も指定できますが、起動ごとにバージョンが変わる可能性があります。バージョン指定を省略するだけでは、uvx がキャッシュを再利用するため同じ意味にはなりません。[uv のツールバージョン説明](https://docs.astral.sh/uv/concepts/tools/#tool-versions)も参照してください。「最新」は公開済みパッケージを意味し、リポジトリの未公開変更は含みません。

### ソースまたは pip からインストールした場合

以下で説明する編集可能なソースインストールの場合は、ローカル変更を保存し、対象ブランチを確認したうえで、元のリポジトリ内で更新してください。同じ Python 3.12 環境へ再インストールします。

```sh
git pull --ff-only
.venv/bin/python -m pip install --require-hashes -r requirements.lock
.venv/bin/python -m pip install --no-build-isolation --no-deps -e .
.venv/bin/python -m goals_iterm_mcp --help
```

Git が更新を拒否した場合は、ローカル変更やブランチの分岐を解決してから続けてください。クライアントの Python 絶対パスは、この環境を参照したままにします。pip で PyPI パッケージをインストールしていた場合は、サーバーが実際に使うインタープリターで `/absolute/path/to/.venv/bin/python -m pip install --upgrade goals-iterm-mcp` を実行します。別の環境を更新しても、この MCP は更新されません。

### 再接続して確認する

クライアントの対応する操作で `iterm` MCP を再起動または再接続し、必要ならクライアント自体を再起動します。ファイルの更新だけでは、実行中のサーバープロセスは置き換わりません。Codex では **設定 → MCP servers → Restart**、または Codex の再起動を使用します。[公式 MCP 設定ガイド](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)を参照してください。

再接続後、クライアントで実際に利用できるツール一覧を確認し、`list_sessions` だけを呼び出して接続を検証します。一覧はインストールした版と一致する必要があります。バージョン 0.2.0 では `close_session`、`close_tab`、`close_window`、`clean_all_sessions` を含む 12 ツールです。`main` ブランチのソースを使う場合は、未公開の読み取り専用 `inspect_sessions` が追加され、合計 13 ツールになることがあります。このソース増分を PyPI 0.2.0 の一部として扱わないでください。単独プロセスでのハンドシェイク成功は、既存の会話のツール更新を意味しません。旧一覧のままなら再接続、または新しい会話で再確認してください。更新確認のためにターミナルの作成・終了や入力送信を行う必要はありません。Python の起動に `--reload` を使用しないでください。

ローカルの Agent に次のプロンプトを渡すこともできます。

```text
[MCP クライアント] の既存 goals-iterm-mcp を最新公開版へ更新してください。
現在の起動コマンドとインストール方式を確認し、設定をバックアップしてから
既存の iterm 項目を更新してください。重複登録せず、環境変数、読み取り専用・
session 範囲制限、ほかの MCP サーバーを保持してください。PyPI と GitHub で
公開版を確認し、固定バージョンまたは実際に使う環境を更新して MCP を再接続し、
クライアントで実際に利用可能なツールと読み取り専用 list_sessions を検証してください。
バージョン、設定場所、検証結果、必要な手動再起動を報告してください。
ソースインストールを説明なしに PyPI インストールへ切り替えないでください。
```

## インストールと起動

上記の[事前準備](#事前準備)を済ませてください。ソースからのインストールには Python 3.12 が必要です。リポジトリのディレクトリで実行します。

```sh
python3.12 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements.lock
.venv/bin/python -m pip install --no-build-isolation --no-deps -e .
.venv/bin/python -m goals_iterm_mcp serve
```

`serve` は stdin/stdout で MCP プロトコルのメッセージを待ち受けます。対話型シェルではありません。診断情報は stderr に出力されます。Python の自動再読み込みを使わずに実行してください。

MCP クライアントの設定例です。コマンドのパスを実際の絶対パスに置き換えてください。

```json
{
  "mcpServers": {
    "iterm": {
      "command": "/absolute/path/to/goals-iterm-mcp/.venv/bin/python",
      "args": ["-m", "goals_iterm_mcp", "serve"]
    }
  }
}
```

オプション：

- `--read-only`：公開済みの 0.2.0 パッケージでは、読み取り専用の 3 ツール `list_sessions`、`read_screen`、`read_history` のみを公開します。`main` ブランチのソースでは、未公開の読み取り専用 `inspect_sessions` も追加で公開されます。
- `--session-id <ID>`：指定したセッションへのアクセスに制限します。複数回指定できます。この制限が有効な間は、ウィンドウとタブの作成が無効になります。

デフォルトでは、現在のユーザーのすべての iTerm セッションを操作できます。読み取りと送信には、必ず `list_sessions` が返した正確な `session_id` を指定します。終了ツールは下記の明示的なセレクターも受け付けます。フォーカス、ワイルドカード、プレフィックス、タイトルから対象を推測することはありません。

## MCP ツール

| ツール | パラメーター | 説明 |
| --- | --- | --- |
| `list_sessions` | なし | セッション、タブ、ウィンドウの ID、読みやすい `name` とメタデータを一覧表示します。 |
| `read_screen` | `session_id` | 描画済みの画面行、サイズ、カーソル位置を読み取ります。 |
| `read_history` | `session_id`, `lines=100` | 保持されているスクロールバックを最大 2,000 行読み取ります。 |
| `inspect_sessions` | `session_id=None`, `nickname=None` | **main の未公開増分のみ。** 読み取り専用のクリーンアップ能力監査です。正確なセッション ID または大文字小文字を折りたたんだ一意のニックネームを 1 つ指定するか、両方を省略して認可された可視セッションをすべて調べます。限定された prompt/process/CLI の証拠、活動、識別情報と永続化の観測、阻害要因、対処の提案、参考情報としてのクローズ準備状態を返します。作業やクローズの認可は行わず、入力送信、CLI 終了、レシート保存、セッションのクローズもしません。 |
| `send_text` | `session_id`, `text` | 最大 16 KiB のテキストをそのまま送信します。改行は追加しません。 |
| `send_keys` | `session_id`, `key` | ターミナルのキーシーケンスを 1 つ送信します。 |
| `create_window` | `command`（省略可） | デフォルトプロファイルでウィンドウを作成し、ID を返します。起動コマンドも指定できます。 |
| `create_tab` | `window_id`, `command`（省略可） | 指定したウィンドウにタブを作成します。起動コマンドも指定できます。 |
| `rename_session` | `session_id`, `name`（省略可） | 既存のセッションを改名します。`name` を省略すると未使用のニックネームをランダムに選びます。 |
| `close_session` | `session_id=None`, `nickname=None`, `force=False`, `dry_run=False` | CLI を終了してネイティブ終了を検証した後、選択したセッションを閉じます。`session_id` または `nickname` のどちらか 1 つが必須です。 |
| `close_tab` | `tab_id=None`, `session_id=None`, `nickname=None`, `force=False`, `dry_run=False` | 選択したセッションまたはタブを含むタブを閉じます。セレクターは 1 つだけ指定します。 |
| `close_window` | `window_id=None`, `session_id=None`, `nickname=None`, `force=False`, `dry_run=False` | 選択したセッションまたはウィンドウを含むウィンドウを閉じます。セレクターは 1 つだけ指定します。 |
| `clean_all_sessions` | `force=False`, `dry_run=False` | 初期セッションスナップショットを調べ、許可されたセッションを整理します。デフォルトではビジー、未知、復旧不能なセッションをスキップし、`force=true` ではスナップショット内の許可された全セッションを試行します。 |

### 読み取り専用セッション能力監査

`inspect_sessions` は現在の `main` ソースにある読み取り専用の診断ツールで、未公開の増分です。公開済みの 0.2.0 パッケージには含まれません。`session_id` と `nickname` は相互排他的です。正確な `session_id` または一意のニックネーム（前後の空白を取り、大文字小文字を折りたたむ）を指定すると認可された 1 セッションを調べ、両方を省略すると現在認可されている可視セッションをすべて調べます。セレクターが無効、曖昧、利用不能、または認可範囲外の場合、端末へ書き込まずに失敗します。

各結果にはセッション、タブ、ウィンドウの識別情報と、限定された `prompt`、`process`、`cli`、`terminal_activity`、`business_acceptance`、`close_readiness` が含まれます。証拠の利用可否、観測された活動、安定したプロセス/CLI 識別情報、チャット永続化の観測、阻害コード、対処の提案が示される場合があります。`business_acceptance` は常に `not_observed` で、`close_readiness` は参考情報にすぎません。その `status` は `eligible_if_unchanged`、`blocked`、`unknown` のいずれかで、前者だけが `ready=true` です。`ready: true` でも認可やクローズ成功を意味しないため、ライフサイクル書き込みの直前に再検査してください。このツールは証拠を読むだけで、端末入力、CLI 終了、復旧レシートの保存、ネイティブクローズを行いません。

### 終了ツール

この 4 つの終了ツールはバージョン 0.2.0 に含まれます。完全な契約は[終了ツール実装仕様](docs/closing-tools-spec.md)にあります。

`close_session`、`close_tab`、`close_window` では、セレクターを必ず 1 つだけ指定します。ID は明示的な ID として照合し、ニックネームの代替にはなりません。ニックネームはセッションスコープのセレクターです。カタログ名の前後の空白を取り、大文字と小文字を区別せずに照合します。曖昧な場合はエラーです。タブまたはウィンドウを閉じるとき、セッションセレクターはそのセッションを含むタブまたはウィンドウを選びます。フォーカス、ワイルドカード、プレフィックスによる対象指定はありません。許可リスト外のセッションを 1 つでも含むタブやウィンドウは拒否されます。

通常の終了では、ターミナル入力を送る前に影響を受ける全セッションを事前確認します。ビジー、待機中、または状態不明のセッションがあれば、対象操作全体を拒否します。`clean_all_sessions` はデフォルトでビジー、未知、復旧不能なセッションをスキップし、アイドルと確認できたセッションだけを閉じます。残りのセッションとウィンドウは保持されます。`force=true` では初期スナップショット内の許可された全セッションを試行し、後から追加されたセッションは対象にしません。`force` はアクティビティゲートを回避して中断する権限だけを与えます。許可リスト、曖昧な識別、対象の変更、復旧レコードの書き込み失敗を回避するものではなく、暗黙の `SIGKILL` でもありません。iTerm ネイティブの force による UI 確認スキップは別の機能です。

最初の中断、CLI の終了、ネイティブオブジェクトのクローズより前に、サービスは非公開の復旧レコードを書き込みます。保存するのはメタデータだけで、ターミナル本文、認証情報、チャット内容は保存しません。認識されたチャット CLI は、中断または終了の前に実際の chat ID を提供する必要があります。ID を知るためだけに、実行中または未知の CLI へチャット本文やスラッシュコマンドを送りません。通常のシェルと通常のジョブでは `cli_sessions` は空で、未知の CLI 識別をシェルやジョブとして暗黙に扱うこともありません。現在のプロセスやチャットの識別証拠が利用できない、または対象プロセスに結び付けられない場合はフェイルクローズします（クリーンアップではスキップとして報告できます）。画面の無出力、経過時間、低い CPU 使用率、完了したように見える回答、セッション一覧の `in_progress` は完了の証拠ではありません。CLI の終了は期限内に実行して検証し、終了を検証できない場合はその対象へのネイティブクローズを発行しません。ただし、iTerm の「終了時に自動的に閉じる」設定により、CLI 自身の終了の副作用としてタブが消えることはあります。共有デーモンや名前だけで選んだプロセスを強制終了しません。

現在の復旧サポートは意図的に限定されています。Claude と Codex は、chat ID を結び付けた信頼できるプロセス登録、または現在のプロセスが実際に開いている transcript/rollout ファイルからのみチャットを識別できます。起動引数だけにある UUID は報告されますが、中断は許可されません。Kiro の保存済みセッション一覧と起動引数は現在のチャット識別の証明にならないため、プロセスに結び付いた既知の ID が必要です。証明できない識別は `force` でも拒否されます。Cursor の受動的な経路は、指定された PID が現在開いている認識済みログから得た UUID だけを受け付けます。信頼できるライフサイクル証拠がない限り CLI のタスク状態は基本的に `unknown` であり、アダプターがすべてのチャットや実行中 CLI を自動取得することはありません。

結果には `operation`、`status`、`force`、`dry_run`、`target`、復旧レコードの ID とパス、閉じた・スキップした・失敗した・不明なセッションの一覧が含まれます。`status` は `closed`、`partial`、`refused`、`noop`、`dry_run`、`unknown` のいずれかです。セッション結果には iTerm ID、ニックネーム、`cli_sessions`、中断、終了、クローズの状態が含まれます。チャットレコードには `cli`、`chat_uuid`、`cwd`、識別情報の出所、永続化状態、構造化された再開用 executable/argv が含まれます。`chat_uuid` はチャットを識別する値ですが、それだけで履歴の保存や再開コマンドのテスト成功を証明するものではありません。これらは別の結果フィールドで示されます。クローズ後はトポロジーを更新します。API の確認応答だけではクローズの証明にならないためです。応答の紛失やタイムアウトは `unknown` になり、自動再試行は行いません。拒否、失敗、不明の操作は構造化データを含む MCP ツールエラーとして返されます。クリーンアップによるスキップだけはエラーではありません。部分結果では完了した副作用を報告し、ターミナルを再び開いてロールバックすることはありません。ドライランでは入力送信、復旧レコードの保存、名前の変更、オブジェクトのクローズを行いません。

`create_window` または `create_tab` で作成したセッションには、4〜7 文字の異なる 200 個の名前からランダムなニックネームが自動で割り当てられます。既存のセッションには `rename_session` で名前を付けられます。指定する名前は最大 64 文字で、大文字と小文字を区別せずに重複を確認します。ほかの稼働中セッションが使用している名前は重複して割り当てられません。セッションを閉じると、その名前を再利用できます。名前の候補を使い切った場合は、セッションを作成する前にエラーを返します。終了ツールのニックネームセレクターも同じ稼働中セッションのカタログを使い、照合前に前後の空白を取り、大文字と小文字を区別しません。

読み取りと送信では、まず `list_sessions` から正確な `session_id` を取得します。終了ツールでは上記の規則に従って正確なニックネームまたは明示的な対象 ID を使えます。フォーカスやタイトルから対象を推測しないでください。

対応するキー：`enter`、`tab`、`escape`、`backspace`、`up`、`down`、`left`、`right`、`ctrl_c`、`ctrl_d`、`ctrl_u`、`ctrl_l`。

テキスト内の改行、Enter、制御キーはフォアグラウンドのプログラムが解釈するため、コマンドの実行やプログラムの終了につながる場合があります。送信には `suppress_broadcast=True` を指定し、対象のセッションだけに送ります。応答の `api_acknowledged` は iTerm API の呼び出し確認を示すもので、コマンドの完了状態は `unknown` のままです。失敗やタイムアウト時に自動再送は行いません。

画面と履歴の読み取りは、ターミナルに描画された出力を返します。CLI 内部のエディターのテキストや、生の PTY バイト列ではありません。ツール操作は単一のサーバープロセス内で直列化されますが、ほかの MCP プロセスや手動入力とは調整されません。サーバーを終了すると API 接続のみが切断され、ユーザーのセッションは閉じられません。
